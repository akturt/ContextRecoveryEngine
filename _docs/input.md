# Context Recovery Engine

**Статус:** спецификация продукта, редакция v5 (двухуровневая классификация Finding, усиленный контракт Scanner, расширенные границы)
**Событие:** DataHub AI Hackathon
**Репозиторий:** https://github.com/akturt/ContextRecoveryEngine (origin/master)

## 1. Резюме

Context Recovery Engine (CRE) — новый open-source инструмент, который за две минуты восстанавливает инженерный контекст произвольного Git-репозитория и публикует его в DataHub. Вход — код и документация проекта. Выход — машиночитаемое описание того, из чего система состоит, какие сущности оперирует и на каких основаниях приняты её ключевые решения.

Редакция v5 вводит двухуровневую классификацию: Scanner назначает `Finding` техническую категорию происхождения (`category`), а Recovery — архитектурный тип (`kind`). Контракт Scanner усилен: он производит только наблюдения и не делает выводов. Границы ответственности расширены явным списком всего, что относится к Knowledge Governance и остаётся вне CRE. Главное правило разработки неизменно: любой новый файл создается, только если он вызывается в демонстрации `cre recover → publish → DataHub`.

## 2. Проблема

Существующие AI-инструменты предполагают, что контекст уже создан и хранится в документации, коде, векторной базе или графе метаданных, и специализируются на его извлечении и потреблении. Инженерное знание — обоснования решений, инварианты предметной области, границы контекстов, критерии корректности — в большинстве проектов в машиночитаемом виде отсутствует и распределено между историей коммитов, обсуждениями и памятью разработчиков. Потолок качества агента задается полнотой доступного контекста, и замена модели на более сильную этот потолок не поднимает.

Задача производства контекста отличается от задачи его потребления по классу. Система, которая извлекает инженерное знание из живого проекта и отдает его потребителям в согласованном формате, снимает ограничение на входе. Это проверяемо демонстрацией на репозитории, о котором система не имела предварительных сведений.

## 3. Решение

CRE решает задачу производства контекста, а не его потребления. Пользователь мыслит тремя шагами:

```
Input (репозиторий)
        ↓
Recover (сканер + классификация + LLM-восстановление)
        ↓
Output (контекст в DataHub)
```

Система не требует предварительной настройки репозитория, не генерирует документацию и не берет на себя управление знанием после извлечения. Она производит один артефакт — восстановленный инженерный контекст — и отдает его через адаптеры.

## 4. Демо

Демонстрация фиксируется до написания кода и является единственным источником требований к реализации.

```
cre recover https://github.com/fastapi/fastapi
  → Components, Relationships, ADR Candidates

cre publish
  → сущности в DataHub

DataHub → MCP → LLM
  вопрос: "Почему FastAPI использует Starlette?"
  агент отвечает на основе восстановленного контекста
```

Демонстрация выполняется на публичном репозитории, к которому система не адаптировалась заранее. Продукт готов при выполнении четырех условий: первый содержательный результат — в пределах двух минут; повторный запуск не порождает дубликатов в DataHub; путь от репозитория до ответа агента проходится без ручных шагов; репозиторий содержит README с контрактом, пример прогона и воспроизводимую инструкцию запуска.

## 5. Контракт продукта

Контракт формулируется как обязательство продукта, а не как академическое определение.

**Context, produced by CRE, always contains:**

- **Architecture** — структура системы, ограниченная компонентами и их связями (Relationships как граф зависимостей). Без Bounded Context, Deployment, Runtime, Topology.
- **Domain Entities** — ключевые предметные сущности, которые система оперирует и хранит.
- **Architectural Decisions** — принятые решения с обоснованием и отвергнутыми альтернативами (ADR-кандидаты).
- **Constraints** — инварианты и ограничения, при которых система остается корректной.
- **Evidence** — ссылка на источник в репозитории, из которого сделан каждый вывод.

Главный принцип — **Evidence First**. Каждый восстановленный объект обязан нести поля **Evidence** (откуда взят) и **Confidence** (уровень уверенности). Это первоклассные поля, а не метаданные: без них вывод считается незавершенным. Именно Evidence + Confidence делают продукт научно обоснованным в отличие от большинства AI-инструментов, выдающих голые утверждения. Всё, что не входит в контракт, находится вне объема, кроме явно поименованного расширения версии 0.2 (раздел 11).

## 6. Роли в экосистеме знаний

CRE — единственный производитель знания; остальные узлы потребляют или управляют им. Модель намеренно плоская:

```
Git Repository
        │
        ▼
Context Recovery Engine        (Knowledge Producer)
        │
        ▼
Canonical Context Model
        │
        ├────────► Markdown
        ├────────► JSON
        └────────► DataHub
                      │
                      ▼
               MCP / LLM / IDE   (Knowledge Consumer)
```

Underboss в этой модели находится сбоку и не участвует в конвейере:

```
                Underboss
                     │
                     ▼
      Knowledge Governance Runtime
                     │
                     ▼
      использует CRE как Recovery Module
```

CRE = Knowledge Producer. DataHub = Knowledge Repository. LLM/IDE/MCP = Knowledge Consumer. Underboss = Knowledge Governance Runtime, управляющий знанием после его восстановления. Это архитектурно сильнее формулировки «CRE — облегченный Underboss»: направление зависимости естественно, CRE ничего не знает о Governance.

## 7. Архитектура

Конвейер содержит пять шагов; наружу показываются преобразования данных от факта к классифицированному объекту.

```
Repository → Scanner → Finding(category) → Recovery → Context Object(kind) → Context Model → Adapters
```

- **Scanner** — детерминированный анализ репозитория без LLM. Извлекает только наблюдаемые факты — `Finding`. Scanner не делает выводов: он не определяет Entity, Component, Relationship, ADR или Constraint и не выполняет Recovery. Каждый `Finding` несёт техническую категорию происхождения (`category`) и `evidence`, но не интерпретацию.
- **Recovery** — классификация `Finding` в LLM. Recovery назначает каждому `Finding` архитектурный `kind` (architecture / entity / decision / constraint / relationship) — это вторая, независимая стадия классификации — и строит Context Model. Никакой дополнительной логики сверх классификации и заполнения полей.
- **Context Model** — `context.json`, реализующий контракт раздела 5.
- **Adapters** — сериализация Context Model. JSON и DataHub — первичные; Markdown — бонус; MCP — тот же уровень. Recovery не знает ни про один адаптер.

Структура репозитория минимальна: `src/`, `cli/`, `examples/`, `README.md`, `NON-GOALS.md`. Любой каталог или модуль, не вызываемый в демо, не создается.

## 8. Scanner

Scanner — главная воспроизводимая часть продукта и его ключевая фишка. Он работает без LLM и производит **только факты**.

Формальный контракт Scanner:

> Scanner никогда не делает выводов.
> Scanner производит только наблюдения.

`Finding` — это наблюдение, а не сущность. Примеры корректных `Finding`:

```
package.json содержит fastapi
README содержит "hexagonal architecture"
есть каталог app/domain
есть импорт sqlalchemy
docker-compose содержит postgres
```

Scanner не производит `Architecture`, `Aggregate`, `Capability`, `ADR` и тому подобное — это уже ответственность Recovery.

`Finding` обязан содержать:

- `id` — уникальный идентификатор находки;
- `category` — техническая категория происхождения (первый уровень классификации);
- `evidence` — ссылка на место в репозитории;
- `source` — файл/коммит/узел, из которого извлечено;
- `payload` — сырые данные наблюдения.

`Finding` не содержит интерпретации.

Категории `category` (НЕ архитектурные):

- `code`
- `configuration`
- `dependency`
- `documentation`
- `filesystem`
- `vcs`

Отсутствие LLM делает сканер дешевым, воспроизводимым и пригодным для многократных прогонов при отладке восстановления.

## 9. Recovery

Recovery намеренно примитивен.

```
Scanner → Finding[](category) → LLM → Context Object[](kind + evidence + confidence)
```

Две независимые стадии классификации:

1. **Техническая категория** (`category`) — назначается Scanner на этапе извлечения (code / configuration / dependency / documentation / filesystem / vcs). Это свойство происхождения, а не смысла.
2. **Архитектурный тип** (`kind`) — назначается Recovery на этапе интерпретации (architecture / entity / decision / constraint / relationship).

LLM получает сырые `Finding` и по контракту (раздел 5) назначает каждому `kind` и восстанавливает содержимое Components, Relationships, ADR-кандидатов, Entities, Constraints, снабжая каждый объект полями Evidence и Confidence. Никаких промежуточных этапов, классификаторов или оркестрации. Недостаток данных — повод завершить восстановление конкретной сущности с явным логом, а не подменять результат.

## 10. Canonical Context Model

Единственный внутренний формат — `context.json`, реализующий контракт раздела 5. Он фиксируется до написания логики восстановления, иначе Recovery не имеет точки сборки.

```
Context
├── findings[]                 # сырые наблюдения от сканера: id, category, evidence, source, payload
├── Architecture
│   ├── components              # kind: architecture
│   └── relationships           # kind: relationship (dependency graph)
├── Entities                    # kind: entity
├── Knowledge
│   ├── decisions               # kind: decision  (MVP)
│   ├── constraints             # kind: constraint (MVP)
│   ├── capabilities            # kind: potential_capability (v0.2)
│   ├── runtime                 # v0.2
│   └── invariants              # v0.2
└── Evidence (source ref + confidence)   # на каждом объекте
```

Каждый объект несет `kind`, `evidence`, `confidence`. `context.json` — единственный формат передачи данных между стадиями; промежуточных представлений не вводится.

## 11. Границы MVP

MVP восстанавливает ровно то, что достаточно для демо за две минуты: **Components**, **Relationships**, **ADR-кандидаты** (внутри Knowledge). Architecture намеренно ограничена компонентами и связями — без Bounded Context, Deployment, Runtime, Topology, Capabilities. Каждая сущность несет Evidence и Confidence.

Runtime, Capabilities и Invariants исключены из MVP как самостоятельные исследовательские задачи и переходят в версию 0.2 внутри контейнера Knowledge, не меняя форму конвейера. Тип находки `potential_capability` описан в схеме, но выключен в MVP и помечен `v0.2`.

Выход MVP — каталог `context/` с артефактами `architecture.md`, `entities.yaml`, `adr_candidates.md`, `dependency_graph.json`, `context.json`, `summary.md`.

## 12. Adapters

Слой вывода называется Adapters, потому что Markdown, JSON, DataHub и MCP — одного уровня и добавляются независимо.

- **JSON** — первичный машиночитаемый выход, основа для всего остального.
- **DataHub** — первичный адаптер публикации; преобразует `context.json` в сущности DataHub.
- **Markdown** — приятный бонус для чтения человеком; судьи DataHub на него не смотрят.
- **MCP** — тот же уровень адаптера, отдает Context Model агентам.

Recovery не знает ни об одном адаптере; добавление DataHub не меняет Recovery.

## 13. CLI

Три команды, отражающие действия пользователя: получить, посмотреть, опубликовать.

```
cre recover    # сканер + восстановление → context/
cre inspect    # просмотр восстановленного контекста (сводка)
cre publish    # адаптер DataHub
```

Команда `report` заменена на `inspect`, поскольку «показать» — действие, а «отчет» — нет. Структура CLI допускает добавление команд без переработки существующих.

## 14. Границы ответственности CRE

CRE отвечает только за производство канонического контекста. Явная граница ответственности:

**CRE отвечает за:**
- детерминированное сканирование репозитория (Scanner);
- восстановление инженерного контекста (Recovery);
- каноническую модель контекста;
- сбор доказательств (evidence);
- первичную классификацию находок по технической категории (`category`);
- вторичную классификацию объектов по архитектурному типу (`kind`);
- экспорт (Markdown / JSON / DataHub).

CRE НЕ отвечает ни за одну из следующих вещей. Все они относятся к **Knowledge Governance**, а не к **Knowledge Production**, и сознательно оставлены вне CRE:

- Design System;
- Discovery Layer;
- Backlog (включая Active/Archive backlog);
- Feature Candidates;
- Legacy Investigation;
- Knowledge Router;
- Runtime;
- Bootstrap;
- Entry Points (managed);
- Design Drift;
- Documentation Governance;
- Knowledge Lifecycle;
- Agent Runtime.

Если начать переносить отсюда, например, Discovery Layer, то через неделю после хакатона снова придётся разделять продукты. Поэтому полный список выше остаётся исключительно на стороне Underboss как Knowledge Governance Runtime (раздел 26).

## 15. NON-GOALS

Файл `NON-GOALS.md` защищает проект от расползания во время хакатона и дублирует границу раздела 14 в пользовательском виде.

```
This project is NOT:
- Documentation Platform
- Knowledge Base
- Runtime
- MCP Server
- Workflow Engine
- Documentation Generator
- Architecture Framework
- Knowledge Governance Runtime
- Backlog Manager
- Registry / Bootstrap
- Design System
- Discovery Layer
- Feature Candidates
- Legacy Investigation
- Knowledge Router
- Entry Points (managed)
- Design Drift
- Documentation Governance
- Knowledge Lifecycle
- Active / Archive Backlog
- Agent Runtime

It only recovers engineering context.
```

Любое предложение «добавить ещё» проверяется по этому списку. Попадание в NON-GOALS — основание не реализовывать.

## 16. Бюджет и ограничения

Доступный объем — 18–22 часа: 8-го участник отсутствует, 9-го возвращается, к вечеру 10-го продукт готов, 11-е — README, схема, видео, подача. Бюджет определяет продукт как небольшой законченный инструмент с одной функцией.

Проектирование по YAGNI: абстракция вводится при появлении второго потребителя. Любая абстракция, не задействованная в демо-сценарии, удаляется.

## 17. Вне области работ

Исключены разработка runtime, веб-интерфейс, отдельный MCP-сервер как самостоятельный продукт, механизмы управления знанием после извлечения и любые формы универсального фреймворка восстановления. Список NON-GOALS (раздел 15) и границы ответственности (раздел 14) имеют приоритет над расширениями.

## 18. Рассмотренные альтернативы

| Вариант | Шанс завершить | Шанс заинтересовать |
|---|---:|---:|
| Полная интеграция в существующую R&D-платформу | 5% | 70% |
| Recovery как модуль внутри платформы + DataHub | 40% | 75% |
| **Context Recovery Engine (отдельный OSS-продукт)** | **85%** | **85%** |
| Reality Drift Engine | 80% | 70% |

Полная интеграция отклонена по объему и стоимости объяснения. Модуль внутри платформы отклонен из-за за риска утонуть в согласовании моделей данных. Reality Drift Engine не использует DataHub и теряет очки по одному из критериев. CRE выбран как вариант с наилучшим сочетанием реализуемости, оригинальности и связи с DataHub.

## 19. План: milestones

Работа разбита на milestones, которые можно параллелить по вертикальным срезам.

| Milestone | Содержание | Результат |
|---|---|---|
| M1 | recover (сканер + минимальное восстановление) | локальный `context/` без адаптеров |
| M2 | + JSON Adapter | машиночитаемый выход |
| M3 | + DataHub Adapter | публикация в DataHub (критический путь) |
| M4 | CLI (`recover` / `inspect` / `publish`) | законченный интерфейс |
| M5 | README, контракт, позиционирование | подача |
| M6 | архитектурная схема, видео | демонстрация |

DataHub Adapter (M3) — первая задача второго дня, поскольку от него зависит критерий «Use of DataHub».

## 20. Организация исполнения

Работа ведется субагентами по вертикальным срезам, а не по файлам. Каждый агент меняет минимальное число файлов, что резко снижает конфликты при интеграции. Постановка вида «сделай Context Recovery Engine» не используется.

| Агент | Задача | Результат | Порядок |
|---|---|---|---|
| Product | README, позиционирование, demo story | полностью независимо | параллельно |
| Architect | Canonical Context Model, интерфейсы модулей | `context.json` + сигнатуры | до начала кода |
| Backend A | Repository Scanner (Finding[]) | детерминированный сканер | независимо |
| Backend B | Recovery Engine (Classification) | LLM-восстановление | после M1/M2 |
| Backend C | DataHub Adapter | публикация | после фиксации выходной модели |
| CLI | команды и UX | `recover`/`inspect`/`publish` | в конце |
| Reviewer | аудит границ, удаление лишнего | сокращение объема | после каждого milestone |

## 21. Обязательные инварианты

Правила действуют на всю кодовую базу без исключений.

1. **Запрет на перенос чужого кода и инфраструктуры.** Исходный код и инфраструктура других проектов не копируются; допускается только точечное заимствование алгоритмов с адаптацией под `context.json`.
2. **Запрет на repo-wide fallback.** При недостатке данных или сбое — fail-fast с понятным логированием, не тихая подмена результата. Продукт либо выдает явный результат с Evidence, либо явно сообщает о невозможности восстановить сущность.
3. **Терминологическая строгость.** Терминология зафиксирована в контракте (раздел 5). Устойчивые термины вроде `Runtime` применимы только там, где соответствующая сущность буквально отражена в коде или модели; в MVP термин `Runtime` не используется вовсе.
4. **Evidence First.** Каждый объект Context Model обязан содержать `evidence` и `confidence`. Объект без них считается незавершенным и не сериализуется.
5. **Правило нового файла.** Файл создается, только если он вызывается в демонстрации `cre recover → publish → DataHub`; иначе не создается.

## 22. Риски

Главный риск — расползание объема: возврат к мышлению фреймворка, расширение стадий, универсальные абстракции, повторное затягивание смежных подсистем внутрь CRE. Митигация: инварианты раздела 21, список NON-GOALS, границы ответственности (раздел 14) и проверка каждого файла вопросом «нужен ли он для демо».

Экспорт в DataHub — на критическом пути оценки и технически последний. Митигация: адаптер — первая задача второго дня в минимальном виде на один тип сущности.

Восстановление на незнакомом репозитории может дать шумный результат. Митигация: демо-репозиторий фиксируется заранее и прогоняется до записи видео, оставаясь публичным и посторонним для системы.

Реализация аналитики с нуля (без переиспользования готового кода) увеличивает объем разработки. Митигация: точечное взятие проверенных алгоритмов при реальной необходимости без переноса окружающей инфраструктуры.

Ценность результата требует измеримой формулировки практической пользы (сокращение онбординга или снижение числа ошибочных изменений), а не декларации уровня «стало проще».

## 23. Архитектурный аудит границ продукта

Перед началом кодирования проводится аудит, цель которого — не улучшить архитектуру, а проверить, не нарушены ли границы ответственности. Аудит поручается субагенту по следующему промпту.

### Prompt — Product Boundary Audit

```
Ты Principal Software Architect.

Контекст.

Разрабатывается Context Recovery Engine (CRE) — самостоятельный open-source продукт для DataHub AI Hackathon.

CRE является исключительно Knowledge Producer.

Он НЕ является частью Underboss Runtime и не должен наследовать его архитектуру.

Во время анализа были рассмотрены несколько идей, возникших при эксплуатации Underboss (Discovery Layer, Feature Candidates, Legacy Investigation, Knowledge Routing, Design System и др.).

Задача.

Проведи минимальное уточнение спецификации CRE.

Главная цель — усилить архитектурную границу между Scanner и Recovery, не расширяя scope продукта.

Не добавляй новые функции.
Не добавляй Runtime.
Не добавляй Knowledge Governance.
Не добавляй Discovery Layer.
Не добавляй Backlog.
Не добавляй Feature Candidates.
Не добавляй Legacy Investigation.
Не добавляй Design System.
Не добавляй Knowledge Router.

Разрешается внести только два изменения.

1. Усилить контракт Scanner.

Scanner должен быть формально определён как источник исключительно детерминированных наблюдений (Findings).

Scanner не имеет права:
- делать архитектурные выводы;
- определять Entity;
- определять Component;
- определять Relationship;
- определять ADR;
- определять Constraints;
- выполнять Recovery.

Scanner только извлекает наблюдаемые факты.

Каждый Finding обязан содержать:
- уникальный идентификатор;
- category;
- evidence;
- source;
- payload.

Finding не содержит интерпретации.

2. Усилить модель Finding.

Ввести первую стадию классификации.

Finding получает только техническую категорию происхождения.

Минимальный набор:
- code
- configuration
- dependency
- documentation
- filesystem
- vcs

Это НЕ архитектурная классификация.

Архитектурная классификация (architecture/entity/relationship/decision/constraint) остаётся исключительно ответственностью Recovery.

Таким образом появляются две независимые стадии:

Repository
    ↓
Scanner
    ↓
Finding(category)
    ↓
Recovery
    ↓
Context Object(kind)

Это разделение должно быть явно отражено в спецификации.

Требования.

- Не менять философию продукта.
- Не менять публичный CLI.
- Не менять Canonical Context Model.
- Не добавлять новые этапы Pipeline.
- Не увеличивать объём MVP.
- Не вводить новые каталоги.
- Не создавать новых адаптеров.
- Не использовать терминологию Underboss.

После изменений проверь, что через неделю после хакатона CRE можно импортировать в Underboss как Recovery Module без изменения архитектурной модели.

Любое изменение, которое усиливает зависимость CRE от Underboss или Knowledge Governance, считать архитектурной ошибкой и отклонить.

Итоговый вывод: из всех наработок Underboss в CRE стоит перенести только усиление границы Scanner ↔ Recovery и более строгую модель Finding. Всё остальное снижает чистоту архитектуры продукта и противоречит его заявленной роли Knowledge Producer.
```

## 25. Соответствие критериям судейства

Критерии оцениваются с равным весом: использование DataHub, оригинальность и практическая польза. Использование DataHub обеспечивается тем, что платформа — получатель результата и точка доступа агентов. Оригинальность — сменой роли DataHub с источника контекста на его получателя. Практическая польза — применимостью конвейера к любому репозиторию без подготовки.

## 26. After Hackathon

Единственный раздел, где раскрывается происхождение проекта.

CRE порождён идеями частной R&D-системы, но развивается как независимый публичный продукт. Направление зависимости естественно: не CRE зависит от R&D-системы, а R&D-система использует CRE как библиотеку.

```
Private R&D → породил идею → Context Recovery Engine → DataHub
После хакатона: R&D-система → Recovery Module → использует CRE как библиотеку
```

R&D-система выступает **донором алгоритмов, а не донором архитектуры**: берутся идеи и конкретные проверенные алгоритмы (детерминированный сбор зависимостей, инвентаризация сущностей), вся инфраструктура остается в R&D-системе. В первые шесть часов работы репозиторий донора не просматривается, чтобы не начать строить его заново.

**Критерий правильности границы.** Если через неделю репозиторий CRE можно удалить, импортировать как библиотеку в R&D-систему и не менять ничего концептуально — архитектура верна. Если для этого потребуется переносить Runtime, Registry, Bootstrap или другие подсистемы — граница проведена слишком широко. Цель — CRE как самостоятельный продукт, а не «Underboss Lite».

К Underboss как Knowledge Governance Runtime относится всё остальное, что CRE знать не должен: Discovery Layer, Knowledge Routing, Feature Candidates, Legacy Investigation, Reality Engine, Documentation Drift, Design Drift, Knowledge Governance, Backlog, Knowledge Lifecycle. Именно эти вещи — причина существования Underboss; перенос любой из них в CRE разрушает чистоту границы Knowledge Producer.
